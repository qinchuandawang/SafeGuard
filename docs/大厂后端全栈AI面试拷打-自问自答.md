# SafeGuard 大厂后端 / 全栈 / AI 应用开发面试拷打

> 使用方式：先遮住“求职者回答”，只看“面试官问题”口述；再对照答案检查是否讲清目标、方案、取舍、故障和数据。本文按项目源码与当前仓库文档整理，不能把尚未实测的目标指标说成线上事实。

## 一、面试定位与项目主线

### 面试官：用三分钟介绍项目。

### 求职者回答：

SafeGuard 是一个面向文本、音频、视频反诈检测的 AI 应用平台。用户可以通过微信小程序提交文本、语音或视频，系统返回风险等级、证据和处置建议；管理员可以在 Web 后台查看任务、模型和知识库。

技术上采用模块化单体 Spring Boot 作为业务中枢，MySQL 保存用户、任务、检测记录和模型配置，Redis 保存任务快照、短期上下文和分布式协调状态，RocketMQ 承担慢检测任务的可靠异步事件链路，MinIO 保存原始媒体。音频和视频模型分别由 Python 服务承载：音频使用 Wav2Vec2，视频使用 Xception。DeepSeek 通过 Spring AI 负责文本分析、风险解释和报告生成；多模态任务由 LangGraph 并行调用文本、音频、视频节点，完成证据融合、人工复核和恢复。

我在后端主要负责检测任务编排、幂等和状态机、推理容量治理、LLM Gateway、任务事件、历史记录和报告生成等模块；项目中的 Python 编排、前端和模型训练由其他成员负责，我对接口契约和链路集成负责。最有技术含量的问题是慢推理场景下如何同时控制重复请求、有限 GPU 并发、任务可靠执行和实时反馈，因此设计了“业务幂等键 + MySQL 唯一约束 + RocketMQ 异步消费 + Redisson 可过期推理许可 + Redis 快照 + SSE 恢复”的链路。

### 面试官追问：为什么不用一个大模型直接判断所有内容？

### 求职者回答：

大模型擅长语义理解和解释，但不适合替代音频伪造和视频换脸专用模型。专用模型输出可量化的概率和证据，大模型负责文本风险理解、跨模态解释和报告生成。这样可以隔离模型职责，便于单独评估、替换和限流。最终报告必须同时保留原始证据、模型版本和融合规则，不能只保存大模型的一段自然语言结论。

### 面试官追问：这个项目最容易被质疑的地方是什么？

### 求职者回答：

第一，模型概率不等于真实概率，融合权重需要验证集校准，不能只凭经验配置。第二，当前 LangGraph Checkpoint 使用编排服务本地 SQLite，适合单实例演示；真正多实例部署需要共享 Checkpoint 存储，或把恢复状态迁移到持久化数据库。第三，RocketMQ 事务消息只能解决生产端本地事务和消息提交的一致性，不能自动保证消费业务幂等和最终完成。第四，性能指标必须给出测试环境、是否包含外部 LLM、样本类型和统计口径。

## 二、多模态编排与风险融合

### 面试官：多模态任务从上传到完成的完整时序是什么？

### 求职者回答：

入口先校验身份、文件类型、大小和请求幂等键，然后计算文件哈希并确定活动模型版本。Java 在主库创建任务和检测记录，状态初始化为 queued，同时保存媒体对象 Key，不把大文件放进 MySQL。任务事件通过 RocketMQ 发布，消费者取得任务后做状态条件更新，将任务推进到 processing。

执行阶段，Java 调用 Python LangGraph 编排服务。文本、音频、视频三个 primary 节点从同一个状态启动，并行执行；各节点捕获自己的异常，写入 errors，不让一个模态异常直接杀死整个图。fuse 节点读取可用结果，按配置权重归一化融合；高置信度结论冲突时进入 human_review，低置信度且有备用模型时进入 fallback。人工审核调用 resume 恢复 Checkpoint，之后 finalize 输出最终状态。Java 接收结果后写入最终记录，Redis 写入快照，前端通过 SSE 读取状态变化。

### 面试官：你们的融合公式是什么？有什么问题？

### 求职者回答：

当前是对可用模态做加权平均并重新归一化：fused = sum(probability_i * weight_i) / sum(available_weight_i)，confidence = abs(fused - 0.5) * 2。视频不可用时，不应把视频权重当零再直接平均，而是只在可用模态权重总和上归一化。当前 fake 阈值为 0.55，real 阈值为 0.45，中间是 uncertain；高置信冲突进入人工审核。

这个方法解释性强，适合第一版，但它假设各模型输出已校准且模态相互独立，实际上未必成立。进一步应在独立验证集上做 Platt scaling 或 isotonic calibration，比较加权平均、逻辑回归和 stacking，并按误报成本选择阈值。反诈场景不能只看 accuracy，还要看 Recall、Precision、F1、PR-AUC、误报率、漏报率和人工复核比例。

### 面试官追问：如果文本说正常、视频说伪造，为什么不取 max？

### 求职者回答：

直接取 max 会放大单个模型的误报，也无法体现模型校准和证据质量。当前做法是先判断高置信冲突，冲突时交人工审核；如果业务要求宁可误报不能漏报，可以增加高风险 veto，但必须明确这是业务规则，不应伪装成统计融合。融合结果还应返回各模态概率、modelVersion、evidence、缺失原因和 calibrationVersion，保证可审计。

### 面试官追问：LangGraph 和 Java 后端分别负责什么？

### 求职者回答：

Java 管业务事实：用户、权限、任务生命周期、幂等、数据库记录、MQ 事件、SSE 查询和管理端操作。LangGraph 只管一次多模态推理的节点编排、分支、Checkpoint 和人工审核中断。这样 Python 编排服务重启或版本变化不会直接改变业务任务事实来源，也避免 Java 和 Python 同时写任务状态产生双写冲突。

当前编排服务 Checkpoint 是本地 SQLite，因此恢复能力主要适用于单实例或固定实例。若要水平扩展，应使用共享持久化 Checkpoint，或者让 LangGraph 只返回中间结果，人工审核状态和恢复参数由 Java 持久化，并通过任务 ID 重建工作流。

## 三、Spring AI、Function Calling 与 LLM Gateway

### 面试官：Spring AI Function Calling 的调用流程是什么？

### 求职者回答：

后端把工具注册为带名称、描述和参数 schema 的 ToolCallback，Spring AI 将工具定义放入模型请求。模型返回 tool call 后，框架根据名称找到 callback，校验参数并执行工具，再把工具结果作为 tool message 回传给模型；模型根据工具结果生成最终结构化响应。后端不依赖解析 Action 文本。

工具执行层需要做白名单、参数校验、超时、权限和审计。模型只能选择允许的工具，不能由模型自由拼接 URL、SQL 或系统命令。工具返回值要限制大小，并明确错误是可重试、可降级还是直接失败。

### 面试官追问：为什么 Function Calling 不是安全边界？

### 求职者回答：

Function Calling 只解决调用格式结构化，不保证模型意图正确，也不阻止恶意参数。真正的安全边界在服务端：工具白名单、DTO 校验、用户权限、资源级授权、超时和速率限制。知识库写入、模型切换、人工审核等有副作用的工具，还要增加管理员权限、幂等键、审计日志和人工确认。

### 面试官：LLM Gateway 统一做了什么？

### 求职者回答：

LLMService 统一承接供应商调用，按场景管理模型、Prompt 版本、温度和 token 上限；调用前做 Token 预算预占，调用后按 provider usage 对账，失败或超时释放预占额度；确定性场景使用精确缓存；统一处理 timeout、有限重试、fallback、错误分类、traceId 和 usage 账本。业务模块不各自创建客户端，避免预算、缓存、重试和观测口径不一致。

### 面试官追问：为什么不能缓存所有 LLM 请求？

### 求职者回答：

随机性、上下文、时间和用户权限都会影响结果。只对输入语义和业务上下文确定、且允许复用的场景缓存；缓存键至少包含归一化输入、模型 ID、模型版本、Prompt 版本、知识库版本、工具版本和关键推理参数。缓存结果要带过期时间和 schema 版本。流式输出可以缓存完整结果后再按 SSE 分片回放，不能把半截结果当成功缓存。

## 四、混合 RAG 与记忆系统

### 面试官：混合 RAG 具体怎么做？

### 求职者回答：

知识入库时先做解析、清洗、混合切块，生成 embedding 后写入 Qdrant，同时保存文档 ID、版本、来源、可信度、权限和时间等元数据。查询时并行执行向量召回和关键词召回，再做权限、时间、可信度和规则过滤，合并候选并 rerank，最后截断成有限上下文交给模型。

记忆分三层：MySQL 持久化会话历史，Redis 保存多实例共享的近期窗口，Caffeine 保存本机热点副本；高价值事实提取成摘要后单独嵌入记忆库，与系统知识库隔离。检索记忆时按语义相似度、可信度和时间衰减重排，不能把用户的一句话直接当作系统事实。

### 面试官追问：为什么记忆和知识库隔离？

### 求职者回答：

两者的生命周期、权限和可信度不同。系统知识库由管理员维护，用户记忆是个体上下文，可能错误、过期或包含敏感信息。混在一个 collection 中会导致普通知识查询召回用户隐私，也难以做删除、审计和版本管理。隔离后可以分别设置 collection、过滤条件、TTL、权限和删除策略。

### 面试官：Recall@5 0.847（562 条评测集）是怎么测出来的？如何证明口径可信？

### 求职者回答：

固定评测集、query、相关文档标注、切分方式和随机种子，保留纯向量基线与混合 RAG 结果；按问题类型、长短问题、时间敏感问题和低频词分桶，报告命中定义、样本量和置信区间。评测集与原始结果见 `performance/rag/`（cases.json 562 条、ragas-eval-result.json）。这个指标只说明检索召回能力，不等于最终回答质量，还要评估 MRR、nDCG、答案 groundedness、幻觉率、延迟和 token 成本。

### 面试官追问：召回错误知识，如何避免模型照单全收？

### 求职者回答：

检索侧做权限、时间、来源可信度和规则过滤；Prompt 要求只依据带来源上下文回答，证据不足时输出不确定；输出侧做引用完整性和敏感内容校验。高风险结论返回证据片段和来源，并由规则或人工审核兜底。RAG 是降低幻觉的手段，不是事实正确性的证明。

## 五、推理容量、并发与热点治理

### 面试官：为什么需要 Redisson 信号量？线程池不够吗？

### 求职者回答：

线程池只能限制单个 JVM 的执行数，多实例部署时每个实例都会各自放行。Redisson 可过期许可把模型并发抽象为集群共享的有限库存。音频、视频按模型独立配置 permits，避免视频长任务占满音频资源；本地有界线程池负责隔离等待和执行，队列超过上限时快速拒绝。

许可必须在确定活动模型后获取，避免按 A 模型占位却调用 B 模型。使用 expirable permit，正常完成主动释放，进程崩溃由租约回收；进程存活时按 lease 的三分之一续租。Redis 开启但协调不可用时应 fail closed 返回 503，不能退化成每实例本地限额导致总容量失控；只有明确单机开发模式才用 JVM Semaphore。

### 面试官追问：相同视频热点合并怎么保证并发安全？

### 求职者回答：

业务键由 sha256(file) + modelId + modelVersion 组成。入口先查任务，再用 Redis 原子占位做快速去重，创建任务时由 MySQL 唯一索引做最终竞争裁决。抢到占位的请求创建任务，其他请求返回同一个 taskId 或订阅同一个任务；创建失败时用 compare-and-set 释放自己的占位，不能无条件删除。

### 面试官追问：文件哈希会不会成为瓶颈？

### 求职者回答：

大文件哈希应流式读取，避免一次性加载内存；上传可以边写对象存储边计算 hash，或采用分片 hash。哈希消耗 CPU 和 IO，需要纳入上传限流。安全上还要校验真实类型、大小、解压炸弹和媒体解析边界，不能只相信扩展名。

## 六、可靠任务、RocketMQ 与状态机

### 面试官：RocketMQ 事务消息解决了什么？

### 求职者回答：

它解决本地数据库事务提交和消息对外可见之间的一致性：先发半消息，Broker 暂不投递；本地事务创建或更新任务和事务记录；成功提交消息，失败回滚。生产者在本地提交后、返回 Broker 前宕机时，Broker 可以回查本地事务状态。

它不解决消费端重复投递、消费完成后的外部副作用、下游执行超时和最终业务失败。消费端仍要做 consumerGroup + messageId 幂等占位、事务内处理和完成标记、重试、死信告警及补偿扫描。

### 面试官追问：为什么不用 Outbox？

### 求职者回答：

Outbox 是更通用、实现更直观的方案：业务事务内写任务和 outbox 事件，后台 relay 投递 MQ，消费者幂等。RocketMQ 事务消息能减少 outbox 轮询，但依赖 Broker 回查和生产者事务监听器，运维与排查成本更高。两者都不能省略消费幂等。如果团队已有统一 Outbox 平台，我会优先复用；本项目选择事务消息是为了满足可靠业务消息的演示和实践目标。

### 面试官：状态机如何防止状态回退？

### 求职者回答：

状态迁移由服务端定义，例如 queued -> processing -> completed/failed，人工审核是 waiting_review -> completed。每次更新带当前状态条件和版本号，例如 where task_id = ? and status = ? and version = ?，成功更新才推进版本。终态更新必须幂等；进度只能单调增加。数据库条件更新和状态迁移方法是最终防线，Redis 快照只是加速读取。

## 七、SSE、缓存、数据库与前端

### 面试官：为什么 SSE，不用 WebSocket？如何断线恢复？

### 求职者回答：

检测进度和 LLM token 都是服务端单向推送，SSE 基于 HTTP，重连和部署更简单；双向实时对话再使用 WebSocket。每条事件带 event ID，客户端重连时携带 Last-Event-ID；服务端从 Redis 快照或 MySQL 恢复当前状态，并在有事件历史时补发缺失事件。即使没有完整事件日志，也要保证 completed/failed 终态可通过查询恢复。

### 面试官：Redis 和 Caffeine 分别缓存什么？Redis 宕机怎么办？

### 求职者回答：

Caffeine 缓存单实例热点，如 embedding、RAG 结果、知识上下文和健康状态；Redis 保存跨实例任务快照、活动模型、短期会话、幂等快速占位和推理许可。普通缓存故障可以回源；任务查询回源 MySQL；推理容量、全局预算和关键幂等协调不可用时 fail closed，不能每实例各自放行。MySQL 是最终事实源。

### 面试官：为什么用主键游标归档？

### 求职者回答：

offset 越到后面扫描越多，且归档过程中数据变化会造成页漂移。使用主键游标 id > lastId order by id limit batchSize，每批在事务内复制、校验，再逻辑删除热表。批次要小，避免长事务、锁等待和 undo 膨胀；失败从上次游标重试。归档锁只防止多实例重复执行，不能替代数据库事务。

### 面试官：小程序和 Vue 后台如何保证安全？

### 求职者回答：

前端路由守卫只是体验层，真正权限校验在后端 JWT、角色和资源授权。文件上传做大小、真实 MIME、时长和解析校验，原始媒体存 MinIO，使用短时授权 URL；管理操作记录操作者、原因和前后值。列表和详情接口必须校验资源归属，防止修改 taskId 或 userId 越权读取。

## 八、Java、Python 和 AI 基础追问

### 面试官：Spring 事务有哪些坑？

### 求职者回答：

同类方法自调用会绕过代理，异常被吞可能导致提交，异步线程不继承事务，事务内调用远程服务会形成长事务，消费确认早于数据库提交会丢业务。项目把本地事务放在 service 层，远程模型调用放到事务外的异步任务，消费幂等和业务副作用放在同一事务，并按异常类型决定重试或回滚。

### 面试官：线程池参数怎么定？

### 求职者回答：

按 CPU、IO、外部推理分别隔离，核心线程、最大线程、队列和拒绝策略由下游容量和压测反推。视频线程池不能超过 GPU 推理许可；队列必须有界，满载时返回 429/503 或持久化 queued。监控 active、queue、reject、task age 和执行耗时。

### 面试官：模型输出为什么不能直接信？

### 求职者回答：

LLM 输出要经过 JSON schema、枚举、范围和长度校验；概率模型要区分 score、probability 和 calibrated probability；阈值要在验证集上确定。解析失败有限重试或降级规则引擎，报告保存模型版本、Prompt 版本、证据和校准版本。CoT 不应作为审计事实，审计依赖工具调用、证据和最终结构化结果。

## 九、性能指标的正确讲法

### 面试官：你简历中的指标怎么证明？

### 求职者回答：

“100 次重复请求 Token 为 0、缓存命中 P95 28ms”已在 `exact-cache-repeat-result.json` 验证：唯一编号文本保证冷启动，随后 100 次完全相同请求，Token 以 MySQL `llm_usage_record` 账本行级对账（重复阶段 0 条记录），命中延迟 P50 5ms / P95 28ms / max 29ms。并发情况下还要测试 single-flight，避免缓存击穿。

“Recall@5 0.847（562 条评测集，`ragas-eval-result.json`）”需要固定评测集、相关文档标注、切分和命中定义，并报告样本量、分桶、置信区间及延迟变化。它只说明检索召回，不等于回答准确。Agentic 反思补检相对基线无实质提升（Recall@5 +0.0006），已如实记录。

任何吞吐和 P95 都要说明单机或集群、CPU/GPU、模型是否预热、是否包含上传、MQ、数据库、Python 推理、LLM 网络和前端端到端。当前仓库文档明确说明部分异步压测关闭外部 LLM，因此不能包装成完整 AI 报告性能。

## 十、面试官的最终评价标准

项目讲得好的候选人，不是能背出最多组件，而是能清楚回答：业务约束是什么，谁是真实数据源，为什么选择这个方案，失败时系统做什么，如何防重复和状态回退，指标如何复现，哪些代码自己真正写过，当前实现的边界在哪里。

最危险的回答包括：“RocketMQ 保证了不丢消息，所以不会重复”“Redis 挂了就本地降级”“Function Calling 天然安全”“用了 LangGraph 就是分布式工作流”“Recall 提升所以回答一定更准”“缓存命中快就等于系统吞吐高”“模型概率就是准确率”。这些说法都会引出更深的反例追问。

回答固定采用四步：先说目标和约束；再说主流程和关键数据；然后讲异常、一致性、降级和边界；最后给验证指标和下一步改进。这样才能体现主后端、全栈和 AI 应用开发岗位需要的工程判断力。
